# 面向 Agent 的 stdio MCP Server 设计

状态为待用户审批。需求来源为《需求文档/MCP需求.md》。用户已选择方案 A，并明确完整目录超过 HTTP 响应上限时仍须支持指标检索及后续查询。

## 使用目标与边界

任一支持 stdio 工具调用的客户端均可启动同一 Server。Agent 负责理解“上月各渠道销售额”、澄清候选、选择工具及解释结果。MCP 进程负责参数契约、调用公开 HTTP API、返回结构化事实。服务端负责执行查询、受理构建及观测部署。首版交付七个工具、通用启动说明、中文调用示例和可复核的验证记录。自建 Agent、UI、独立部署写入口、metricPlatform 改造、认证及租户体系均在范围外。

## 考虑过的方案

| 方案 | 收益与代价 | 决定 |
|---|---|---|
| A．服务端按请求扫描固定构建的封存 Manifest，返回一页摘要 | 历史构建可以直接使用，无数据迁移。翻页会重复扫描，需记录大目录下的实测耗时。 | 用户选定。首先解决响应体上限。 |
| B．构建时生成独立资源索引 | 高频查询的读取成本较低，会引入历史回填、索引失败及清理流程。 | 首版不采用。 |

## 工具与 HTTP 边界

以下为设计建议的默认契约。工具输入字段使用 snake_case，嵌套业务模型沿用 HTTP 公开别名，并在发现信息中完整声明。HTTP 地址均相对配置的服务地址。

| 工具 | 交互与结果 |
|---|---|
| get_current_deployment | 仓库、环境 UUID、分支映射到 GET /deployments/current。只取实际生效指针 activeBuildId 和 activeCommitSha。指针为空返回明确的无生效部署状态。 |
| search_catalog | build_id、非空关键词及可选资源类型、limit、cursor 调用新增 GET /builds/{build_id}/catalog/search；返回资源摘要和下一页游标。 |
| get_resource | build_id、resource_id 调用 GET /builds/{build_id}/resources/{resource_id}，返回该构建公开的节点定义和属性。 |
| get_available_dimensions | build_id、一个或多个 metric_resource_ids，解析为服务指标名后调用 POST /query/available-dimensions，build_id 作为查询参数。保留 optionId、显示名、类型、粒度及操作符。 |
| query_metrics | 同一 build_id、已选指标资源 ID 和 HTTP 支持的分组、过滤、排序、起止时间及行数限制；调用 POST /query，固定 mode=QUERY。保留简单分组及按指标绑定的复合分组。绑定键在工具侧为所选指标资源 ID，转换为同一批已解析的服务指标名。维度使用服务返回的 optionId。排序中的维度或绑定列标识沿用 HTTP 语义，指标资源 ID 转为服务指标名。 |
| submit_build | POST /builds。完整小写 SHA 遵循现有 40 或 64 位校验，执行快照、幂等键、仓库、分支及部署策略必填。origin 沿用可选契约。说明成功后部署策略的副作用，HTTP 202 后立即返回受理事实。 |
| get_build | GET /builds/{build_id}，分别呈现构建状态、错误、catalogAvailable 和 initialDeployment 的真实状态。当前 API 缺少独立查询可用性字段，明确返回 unknown 并记入交付缺口，由实际维度或查询请求返回具体失败原因。 |

## 大目录检索和指标身份

搜索端点复用 CatalogService.read 的构建状态及封存产物校验。在内存中读取该构建中现有业务资源白名单内的有效节点，按原生 unique_id 去重。关键词去除首尾空白，对 ID、名称、显示标签及说明做大小写无关子串匹配；类型过滤为精确匹配。结果按 unique_id 升序，同显示名的候选逐条返回；摘要含 ID、名称、类型、说明以及可用的显示标签。完整定义由资源详情读取。

建议 limit 默认 50，范围 1–200。游标绑定构建、规范化关键词、资源类型和上条记录 ID；条件不符或游标无效返回现有非法游标错误。服务端依据实际序列化响应大小缩短本页，游标指向最后一条已返回记录，末页为 null。若单条摘要连同必要元数据也超限，返回明确的大小限制错误。验收的大目录由多个正常大小的资源组成。已有全量目录接口沿用现有行为。

为避免查询依赖客户端下载全量目录或详情中的源码，新增搜索端点还接受互斥的精确资源 ID 查找条件，作为 MCP 内部 HTTP 调用。按指定构建、类型 metric 和原生 ID 精确取得名称；同构建下精确核验该查询名称唯一指向此指标后才调用按名称执行的 HTTP 接口。精确查找由服务端在扫描中完成唯一性检查，并返回可否唯一映射。缺失、非指标或无法唯一映射时返回明确原因，不从 ID 后缀推测名称。此模式无需增加 MCP 工具。显示标签相同但查询名称不同的两个定义均可被独立选择。

## 调用行为及运行方式

Agent 在当前部署场景只解析一次实际构建，显式指定构建时直接开始搜索。所有工具独立接收 build_id，不保存会话级“当前版本”。查询结果原样保留列、行、null、JSON 数值、时区、规范化时间边界及 resultTruncated。成功零行时保留列。中文示例从 get_build 的执行快照取得业务时区，以它解释上个自然月，按 HTTP 时间语义传参，用返回的实际边界解释结果。

建议沿用 Python，在项目提供可选 MCP 依赖和独立命令 dbt-metricflow-mcp。使用 MCP SDK 的 stdio 传输和工具发现机制。通过环境变量 DBT_METRICFLOW_SERVICE_URL 指定 HTTP 地址；直连沿用当前服务访问方式，已有部署若需要 Bearer 凭据，通过可选 DBT_METRICFLOW_SERVICE_TOKEN 传入。stdout 只传输协议，诊断发往 stderr。执行快照仅接受服务定义的 credentialRef 引用。错误与日志避免记录认证头、原始请求体及原始异常中的凭据。

工具返回结构化内容与等价的文本表示，工具执行失败设置 isError，并保留服务错误码、可重试标记和已知构建 ID。区分参数无效、未部署、资源缺失、构建不可查询、HTTP 连接失败。提交后连接中断且受理结果未知时明确报告未知，同一请求的恢复必须复用原输入和幂等键。MCP 不主动重提交。只有部署状态为 DEPLOYED 才报告部署成功。

## 验收与交付记录

1. 用两个独立客户端通过 stdio 启动同一命令，不安装专用 Skill。分别记录客户端名称与版本、七个工具的输入结构，以及读取同一测试部署得到的构建 ID。
2. 使用有已知销售数据的固定构建，先验证完整目录触发大小上限，再经 MCP 搜索、翻页、读取定义、发现渠道选项并查询；与直接 HTTP 调用逐项比对构建、提交、边界、列和行。覆盖同标签指标选择、跨条件错用游标及无匹配。
3. 在分析中途将当前部署由 A 切到 B，后续显式传入 A，验收结果为 A 的数据或 A 的具体错误。区分成功空行、非法维度、无部署、服务不可达。
4. 重复提交同一请求及幂等键，只受理一次。覆盖受理响应丢失后的恢复，以及构建成功、关联部署失败的独立展示。
5. 启动说明列出命令、配置及 stdio 使用方式。验证记录逐项标明真实服务或契约替身、运行版本及实际结果；未运行的场景明确记为未验证。
