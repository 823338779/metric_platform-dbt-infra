# Singleton 性能阈值失败归因

## 结论

这项失败已在本次功能开发前的代码上，通过未修改的原 pytest 用例复现。独立性能断言对照中两版均为 2 次通过、2 次失败；原 pytest 入口对照又证明，运行路径和加载上下文可以反转通过/失败结果，同一旧版本同一路径也会波动。被测实现、测试及辅助代码的源码哈希完全一致。**可以排除“本次新增查询算法使 Singleton 实现变慢”这一解释；这是既有微基准在当前 Windows/Python 环境中的阈值和上下文敏感性问题。**

这里的结论仅针对 `test_singleton.py::test_create_existing`，不等同于整个查询引擎没有性能回归。

## 实验设计

- 基线：`04a659631ac20456d3af31565a4f03ea9eb71c37`，单独 detached worktree；当前：`45849c2e857ed0c910d56eaffe12f0f7f8a55212`。
- 两版使用同一个已安装的 Hatch Python 3.12.14 环境，不重新安装依赖。
- 每次创建新 Python 进程，固定 `PYTHONHASHSEED=0`、`PYTHONUTF8=1`，工作目录和 sys.path 指向对应版本。
- 预先固定 8 次执行顺序：基线、当前、当前、基线、基线、当前、当前、基线。未重复运行直至通过。
- 调用原测试的真实 setup/statement 和原 `assert_performance_factor`。只包装 Timer.autorange 记录返回值，不修改 timer、阈值 0.4、重试次数或计算公式。
- 每次另用高精度 perf_counter 做 3 组固定 300 次循环的配对测量，交替先测左/右，保留全部样本。该对照不作为替代测试通过标准。

## 原 pytest 入口的交叉复核

没有停留在上面的独立计时实验。保持同一解释器、PYTHONHASHSEED=0、`-n 4`，直接运行原用例：

```text
pytest tests_metricflow_semantics/toolkit/test_singleton.py::test_create_existing -q -n 4 -p no:cacheprovider
```

| 对照 | 基线 | 当前 |
| --- | --- | --- |
| 固定 ABBA/ABBA，基线在 N:、当前在 M: | 4/4 通过 | 4/4 失败 |
| 只交换映射，基线在 M:、当前在 N:，第一次 | 失败，比值 0.39 | 通过 |
| 同一交换映射再次验证 | 通过 | 通过 |

第一行单独看会误判为版本回归；交换路径后，**原始旧测试也失败，当前测试也通过**。随后同一旧版本、同一路径又通过，说明也不能把它简化成“某个盘符必然失败”。运行路径会改变 pytest/解释器加载上下文，但计时段本身不读磁盘，本记录不把结果解释成磁盘 I/O 慢。

额外日志探针不替换 Timer、不改变测试断言，只记录已有 performance logger 和测试开始时的状态。两版都没有 tracing/profiling，Singleton 缓存均只有相同的 3 个实例；当前仅多加载了 bound_output_key_spec 模块。加上这类只读观测后，旧版失败、当前版通过。不存在缓存随新增查询分支持续膨胀的证据，微基准却对加载上下文敏感。

这组入口复核的当前版本已包含本轮新增用例提交 `1dcd81c42`；相对 `45849c2e8` 只新增查询测试和夹具，Singleton 及被测辅助源码未变。摘要见 [pytest 上下文对照数据](artifacts/2026-11-18-singleton-pytest-context-results.json)，完整命令输出保留在本工作树 SDD 记录中。一次基线直接从很长的物理路径运行曾在导入阶段失败，使用 N: 短路径后重跑；该导入错误没有计入上述性能样本。

## 为什么此前会“一边通过、一边失败”

本机 thread_time 使用 GetThreadTimes，perf_counter 使用 QueryPerformanceCounter。虽然 get_clock_info 报告的 resolution 都是 1e-7 秒，但本次 **所有** thread_time 实测总耗时都恰为 **15.625ms** 的整数倍，例如 0.3125s、0.328125s、0.421875s。

原 helper 用约 0.2s 以上的 autorange 选择循环数，再分别相除计算比值。几十毫秒的量化变化足以让接近阈值的比值跨过 0.4；原 helper 又在任意一次超过阈值后立刻通过，最多尝试三次。旧版曾通过，不能证明它稳定达到阈值。

高精度对照两版的中位数也均低于 0.4，说明不能简单把计时器换成 perf_counter 就认为门禁应全绿。这个硬阈值本身也需要按基准环境评估，不能为本次功能任意降低。

计时量化是直接观测到的放大因素，但没有把所有加载上下文差异都武断归结为时钟；具体到 CPython 分配器或缓存布局的微观机制，本轮未做更底层剖析。版本/路径交叉复核已经足够证明该失败不专属于新代码，当前这个微基准不能可靠地作为新查询功能的性能回归信号。

本轮不修改 singleton 生产实现、不降低阈值、不增加重试、不跳过失败测试。之前报告中的“第 13 项尚未归因”由本记录补充归因为开发前已经存在、在当前环境不稳定的性能门禁；原生全量检查仍不声称全绿。若后续要修复这个门禁，应独立校准稳定运行环境和测量方法，而非为本次功能调低数值。
