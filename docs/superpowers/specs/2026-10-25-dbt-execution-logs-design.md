# dbt 执行日志持久化

> 后续决定：详细日志已增加 HTTP 查询接口；用户随后要求移除旧阶段日志。有关保留 engine_change 的描述已由 [移除方案](../plans/2026-10-25-remove-stage-log-api.md) 替代。

用户要求新增独立 PostgreSQL 日志表，详细保存 dbt 内部运行过程，尽量不影响业务流程。

采用已讨论的统一采集、脱敏、有界队列和后台批量写库方案。相比结束后保存 stdout 尾部，该方案保留运行中的完整事件消息，且可以在命令结束前查看已提交日志。不采用逐条同步写库，避免数据库延迟进入 dbt 事件回调。

新增 runtime_execution_log 表，记录 build_id、job_id、attempt_id、phase、command、时间、级别、事件名称和代码、invocation_id、节点 unique_id、线程名、消息。现有 engine_change 进度接口保持原义；本次不新增 HTTP 查询接口。

执行层提供可选日志接收器，dbt 回调及已有 Python Handler 共用脱敏入口；运行时在 _dbt 绑定任务上下文，存储层使用独立短事务。DEBUG dbt 事件也保存，消息不受原 stdout 尾部上限限制。只提取明确字段，不保存可能携带敏感信息的完整事件对象。

实现选择：日志写库异常不改变 dbt 结果，停止本次命令后续日志写入并明确告警；队列满时丢弃新增日志并报告丢弃数量。队列最多 2048 条，每批最多 100 条，约 0.5 秒刷新，退出时排空；非持久队列在进程崩溃时可能丢失未提交部分。正常结束、失败和取消均等待引擎停止并刷新日志。

新库初始化纳入新表；现有库通过显式增量 SQL 建表，不在服务启动时自动升级。本次不改 vendor 中已有的用户修改，不修改真实业务库。

验证：真实 dbt parse/build 事件、DEBUG 和节点信息、动态秘密脱敏、日志超出尾部上限、写库异常和队列满、取消清理、PostgreSQL 表映射及任务隔离、现有测试回归。
